# A 域 · 标签体系设计方法（从决策到规格）

> v1.0 的能力是「检查一套已有标签对不对」；本文件补的是**「从零设计一套能用、能维护、能验收的标签体系」**。
> 规则检查 → 设计生成，是 v1.1.0 的主要升级。适用对象与 A 域一致，B 域实体标签走 `label-visual-designer`。

---

## 一、决策反推链（D-Q-D-V）

设计不是「先列一堆维度」，而是**从业务决策倒推**。按顺序写四列，顺序不能反：

```
Decision（要做什么决定）
  → Question（做这个决定必须先回答什么）
    → Dimension（哪个维度能回答这个问题）
      → Value（这个维度有哪些取值）
```

| Decision | Question | Dimension | Values |
|---|---|---|---|
| 首页要不要推这篇 | 内容深度够不够 | `content-depth` | `intro` / `advanced` / `expert` |
| 分到哪个渠道 | 载体形式是什么 | `content-format` | `article` / `video` / `infographic` |
| 能不能对外发 | 举证状态如何 | `evidence-state` | `sourced` / `needs-proof` / `cut` |

**三条硬约束**：

1. **每个维度必须挂到至少一个 Decision**。挂不上的维度删掉——那是「为分类而分类」。
2. **每个 Decision 至少要有一个维度支撑**。没有就说明是**信息缺口**，要补采集，不是补标签。
3. **一个维度不同时服务两个互相冲突的决策**。例如「优先级」既决定推送又决定审核顺序，会逼出一个混合值域；拆成两个维度。

> 这条链的判断力在于第 2 条：多数标签体系失败，不是维度切得不好，而是有人想用标签回答一个**目前没有数据**的问题。

## 二、粒度与基数

| 项 | 建议区间 | 超界时怎么办 |
|---|---|---|
| 维度数量 | 3–7 | 超过 7：多半混了两类业务对象，拆成两套体系 |
| 单维度取值 | 2–12 | 超过 12：考虑拆维度，或改「开放值域 + 取值来源」 |
| 层级深度 | ≤ 3 | 超过 3：把树拆成两个正交维度 |
| 单对象标签数 | 2–5 | 全为 1：维度没设计开；普遍 > 5：维度切太碎 |

**反模式**：把组合塞进一个值，如 `advanced-video-sourced`。一旦要按「视频」筛选，这个值就废了。组合是**多个维度同时打标**的结果，不是一个新值。

## 三、关系模型（五类）

维度之间、取值之间不是一盘散沙。规格书必须输出关系矩阵：

| 关系 | 含义 | 可机械检查 |
|---|---|---|
| `synonym` | 同义，须收敛到规范 ID | ✅ 同名不同 ID → 名漂移 |
| `broader-narrower` | 上下位，同一棵树内 | ✅ 层级深度 |
| `exclusive` | 互斥，不可同时出现 | ✅ 同对象同时命中 → `不通过` |
| `requires` | 依赖，A 出现则 B 必须出现 | ✅ B 缺失 → `不通过` |
| `co-occurs` | 高频共现，仅作提示 | ❌ 只提示，不判错 |

> `co-occurs` 只作提示，是因为高频共现往往来自业务真实结构，不是设计错误。把它判成错误会逼用户拆掉本来合理的组合。

## 四、标注指南：设计落地的最后一公里

**没有标注指南的标签体系，两个人会打出两套结果。** 规格书必须附带标注指南（模板见 `templates/annotation-guide-template.md`），每个维度写全六项：

1. 定义句（什么条件下算这个值）
2. 判定问句（一句话能问出来）
3. 正例
4. 反例
5. **易混淆边界例**（最难的两个值之间怎么划）
6. 不确定时怎么办：标 `unknown` 并进复核队列，**不猜**

第 6 项最关键。允许「猜」的标注指南，等于允许口径漂移从源头产生。

## 五、生命周期

```
draft → active → deprecated → retired
```

| 状态 | 规则 |
|---|---|
| `draft` | 不进生产数据，可用于试标 |
| `active` | 唯一允许新数据使用的状态 |
| `deprecated` | 必须写 `successor` 与迁移窗口；旧数据只读，新数据禁止使用 |
| `retired` | 不再查询，历史数据保留只读，不物理删除 |

`deprecated` 与 `config/rules.json → key_aliases` 联动：旧名保留别名，避免历史数据断链。
**不要直接删旧标签**——这是 v1.0 已经写过的修复方向，在设计阶段就要预留。

## 六、可计算的覆盖度与质量指标

设计是否健康，不能只靠肉眼。跑 `scripts/check_taxonomy_coverage.py`，阈值在 `config/rules.json → coverage`：

| 指标 | 含义 | 不健康的样子 |
|---|---|---|
| `coverage_rate` | 有标签的对象占比 | 大量对象没打上标，体系没铺开 |
| `dimension_coverage` | 每个维度被使用的对象占比 | 某维度几乎没人用，多半是伪需求 |
| `orphan_values` | 样本中出现但未登记的值 | 标注指南没覆盖，或有人在乱打 |
| `long_tail_ratio` | 命中数 ≤ 2 的值占比 | 值切太碎，维护成本失控 |
| `single_tag_rate` | 只打 1 个标签的对象占比 | 维度没设计开 |
| `relation_conflicts` | 互斥值同时命中 / 依赖缺失 | 关系矩阵与实际数据冲突 |

> **指标只说明结构健康度，不说明业务有效。** 覆盖度 100% 的体系也可能全是废标签。业务有效性由用户拍板，不由脚本判定。

## 七、设计评审四问（出稿前必过）

1. 每个维度挂得到至少一个 Decision 吗？
2. 标注指南能让两个人打出同一个结果吗？
3. 覆盖度指标达标吗？未达标的项是设计问题还是样本问题？
4. 有没有哪个维度其实属于**另一个业务对象**？

四问全过才出规格书。任何一问过不了，退回上一节，不要靠「先发一版再改」糊过去。

## 八、设计产出清单

1. 标签规格书（`templates/label-spec-template.md`，含 D-Q-D-V 表）
2. 标注指南（`templates/annotation-guide-template.md`）
3. 关系矩阵（五类关系）
4. 覆盖度报告（`check_taxonomy_coverage.py`，Markdown + JSON）
5. 口径声明（供 `check_label_consistency.py`）与单一事实源

## 九、边界

- 本方法不产出业务系统代码，不自动改线上标签库。
- 覆盖度脚本只算结构与一致性，**不判断标签是否贴合业务、不判断取值语义是否等价**。
- 设计取舍（维度合并、命名恢复、值域拆分）一律单列「待业主拍板」。
