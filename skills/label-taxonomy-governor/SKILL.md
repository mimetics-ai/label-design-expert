# 标签体系设计与文案合规器

把「标签」这件事拆成两个不混用判据的域：**A 域能设计出一套体系，B 域能审清楚一份文案**。

> 版式与视觉设计不在这里，走 `label-visual-designer`；两份结论分开出。

**四条纪律，先记住：**

1. **先分流，不混用判据。** 同一个「这个标签不行」，在 A 域是维度不正交／口径漂移，在 B 域是强制标注缺失／禁用词。没分流就开始查，等于没查。
2. **先设计，后校验。** A 域新建体系必须先走 D-Q-D-V 与标注指南，再跑覆盖度脚本。**脚本只能判断已提出的方案，不能生成方案**——拿校验脚本当设计工具，会得到一份「检查得很仔细但根本没人设计过」的规格书。
3. **脚本只查结构，不判定。** 脚本能找出命名违规、枚举重复、跨文件取值冲突、覆盖度异常、分域禁用词命中，但**没有能力判断某句话是否合法合规，也不能判断标签是否贴合业务**。把脚本输出直接当结论，会产生「看起来检查过了、其实没检查」的假安全感。
4. **没跑脚本就不许说跑过。** 报告首行必须是 `【执行声明】脚本：已运行（N 项）｜未运行（人工逐条）`。编造一次执行记录比漏判十条更严重。

## 触发条件

- 要为一批内容／商品／用户**从零设计**标签体系，或要给现有标签定命名与取值规范
- 要写标注指南、划易混淆边界、定标签生命周期
- 要验收一套体系的覆盖率、长尾值、关系冲突
- 同一标签在规格表、配置、代码常量、文档里取值对不上，要定位漂移点
- 一份产品／包装标签文案要下厂或要上架，需核强制标注与禁用词
- 标签用词被内部判「过强」，但官方技术文件用了同一个词，需要判定是否恢复

## 输入

| 输入 | 必填 | 说明 |
|---|---|---|
| 域 | ✅ | A 数据／内容标签体系、B 商品／包装标签文案、跨域（分别出结论） |
| A 域新建：业务**决策**清单 + 业务对象清单 | A ✅ | 设计必须从决策出发，只有对象清单无法反推维度 |
| A 域验收：现有标签表 + 标注样本 + 关系矩阵 | A ✅ | 用于覆盖度与关系冲突校验 |
| A 域治理：口径声明 | A ⭕ | 用于跨文件漂移检测 |
| B 域：标签文案全文 | B ✅ | 要上机的那一版全文，不是摘要、不是转述 |
| B 域：产品属性认定依据 | ⭕ | 农药／化妆品／食品／普通商品；缺失时标「需人工复核」，不替用户猜 |
| 目标印厂规范 / 项目内部规范 | ⭕ | 用户给了就以用户规范为准，不用通用默认值覆盖 |

> ⚠️ **不要用摘要做核查**。摘要会磨掉限定词、适用范围和版本号，而这些恰恰是判定依据。

## 输出

1. **审查报告**（Markdown）— 执行声明 + 分流结论 + 三栏表 + 待拍板项 + 依据清单
2. **机器可读报告**（JSON）— 由脚本产出，字段结构稳定
3. **A 域新建时**（按 `templates/`）：
   - 标签规格书 `label-spec-template.md`（含 D-Q-D-V 决策链）
   - 标注指南 `annotation-guide-template.md`
   - 覆盖度报告 `check_taxonomy_coverage.py`
   - 关系矩阵与生命周期表
4. **A 域治理时**：口径一致性报告 `check_label_consistency.py`

## 自检

用户说「跑自检／测试一下／检查安装」时，运行 `scripts/self_check.py` 并原样贴出输出（**22 条冒烟断言**）。

## 处理步骤

1. **分流**。判 A / B / 跨域，写进报告首段。跨域先出总检查清单，再按依赖顺序分别执行，**不合并成一句结论**。
2. **索取必要输入**。缺什么列什么，不替用户假设产品属性、业务决策、印厂规范、登记状态。
3. **A 域设计阶段（新建体系时先做，不能跳过）**：
   - 按 `taxonomy-design-method.md` 第一节写 D-Q-D-V 决策链，每个维度必须挂到决策。
   - 定粒度与基数、五类关系矩阵、生命周期。
   - 按 `annotation-guide-template.md` 写标注指南，**六项齐全**，明确「不确定时不猜」。
   - 过设计评审四问。四问不过退回改，不靠「先发一版再改」糊过去。
4. **A 域验收 / 治理**：
   ```bash
   python scripts/check_taxonomy_coverage.py \
       --input taxonomy-design-example.json --config config/rules.json \
       --output-md coverage.md --output-json coverage.json

   python scripts/check_label_consistency.py \
       --input declarations.json --config config/rules.json \
       --output-md report.md --output-json report.json
   ```
   - 覆盖度脚本读 `metrics`、`orphan_values`、`relation_conflicts`；口径脚本读 `summary`、`conflicts`、`naming_violations`、`banned_hits`、`verdicts`。
   - 归一化的口径键用于把 `env.expectedIntegrity` / `EXPECTED_INTEGRITY` 归到同一组；别名表在 `config/rules.json`，不够用就补配置，**不要在脚本里硬编码项目名**。
   - 脚本判不了的（语义是否等价、哪个值是权威、标签是否贴合业务）由模型判断并写明依据；判不了的标 `需人工复核`。
5. **B 域执行**：先做**属性认定**（见 `domain-b-label-compliance.md` 第一节），再逐条查强制标注、分域禁用词、商标标注、用词强弱。**先判适用性再判缺失**——不适用的项不进缺失清单。
6. **逐条三态结论**。只写 `通过` / `不通过` / `需人工复核`。禁止「可能有风险」「基本没问题」「建议咨询专业人士」单独成句。
7. **给依据**。格式 `依据：<文件/法规名称> <条款位置>`；来源不确定写 `依据：待核实`。包内规则表来自项目历史核查，**须提示用户复核现行有效版本**。
8. **单列待拍板项**。口径取舍、命名恢复、维度合并、法规适用判断一律交回用户，给两边论据，不替用户决定。
9. **汇总交付**。Markdown 报告 + JSON + 规格书/标注指南（A 域新建）+ 修复建议清单（按 `阻断交付 / 需修复 / 建议优化 / 需人工复核` 排序）。

## 脚本边界（务必如实转述给用户）

| 事项 | 脚本能做 | 脚本不能做 |
|---|---|---|
| 命名规范 | ✅ 正则、长度、保留词 | ❌ 判断名字在业务上是否贴切 |
| 枚举完整性 | ✅ 重复值、空值、类型混杂 | ❌ 判断枚举是否覆盖全部业务情况 |
| 跨文件口径 | ✅ 同口径键不同取值 | ❌ 换词表述（"客户数" vs "服务企业数"） |
| 覆盖度 | ✅ 覆盖率、维度使用率、未登记值、长尾值、单标签对象 | ❌ 判断业务有效性、标注一致性统计量 |
| 关系矩阵 | ✅ 互斥值同时命中、依赖缺失 | ❌ 判断 `co-occurs` 是否合理 |
| 分域禁用词 | ✅ 按 `scope` 匹配词表 | ❌ 判断整句是否构成违规宣称 |
| 适用性判定 | ❌ | ❌ 必须由模型按属性认定与委托方身份判断 |
| 法规效力 | ❌ 不联网、不查现行版本 | ❌ 必须由用户或法务复核 |

`config/rules.json` 缺失或格式错误时脚本会**报错退出，不静默回退**。报告里必须如实说明脚本有没有跑成功。

## 判定与结论的归属

- **事实部分**（命名是否违规、取值是否冲突、覆盖率、词是否命中）：由脚本与规则包决定，模型不得凭印象下结论。
- **定性部分**（算不算维度重叠、算不算夸大、哪个口径是权威、标签是否贴合业务）：由模型判断，但必须写出依据句。
- **拍板**：删不删、改不改、维度合不合并、发不发，由用户决定。用户坚持保留一条 `不通过` 的内容时，如实记录「此条在已知风险下保留」，不重复劝阻。

## 注意事项

- 本技能**不构成法律意见**，不判断是否违法、不预测处罚。定性交法务。
- **不宣称首创**。本技能的方法论均为既有实践的结构化整理，承袭／增量对照见 `experience-provenance.md`。
- **查不到 ≠ 不存在**：查不到登记状态时只能做材料完备性核查，须说明边界。
- **不适用 ≠ 缺失**：把不适用的项报成缺失，会让用户去准备一份根本不需要的材料。
- **指标不达标 ≠ 业务无效**：覆盖度只说明结构健康度。
- **规则可配置**：所有阈值、词表、别名放 `config/rules.json`，不要把项目专有名词写进脚本。
- 不刷长度。三段话说得清，不写三页。
